# فرمان‌های مدیریت InfraHub

نصب‌کننده جدید فرمان `infrahub` را در `/usr/local/bin` ثبت می‌کند. عملیات فقط روی سرور نصب‌شده و با sudo اجرا می‌شود؛ در این مرحله این فرمان روی میزبان اجرا یا نصب نشده است. محیط Python ابزارها در `.cli-venv` مستقل از Python سیستم است؛ وابستگی‌ها با hash نصب می‌شوند. فایل همنام متعلق به نرم‌افزار دیگر بازنویسی نمی‌شود.

## پشتیبان دستی

```bash
sudo infrahub backup
sudo infrahub backup --destination /srv/infrahub-backups
```

فایل فشرده `infrahub-backup-YYYY-MM-DD_HH-MM-SS_MICROSECONDS.tar.gz` و checksum کنار آن ساخته می‌شود. تاریخ و ساعت نام فایل به وقت تهران است؛ مسیر پیش‌فرض `/opt/infrahub/state/backups` است. پشتیبان شامل dump سازگار MySQL، آپلودها، تنظیمات، کلیدها، سورس و تصاویر Docker نصب‌شده است. برای snapshot هماهنگ، backend کوتاه‌مدت متوقف و دوباره شروع می‌شود. نگهداری تصاویر می‌تواند فضای زیادی مصرف کند؛ ظرفیت کافی و کپی بیرونی لازم است. فایل مجوز 600 دارد ولی رمزگذاری خارجی ندارد؛ شامل کلید و داده حساس است و باید در ذخیره‌ساز محدود/رمزگذاری‌شده نگهداری شود. پشتیبان‌های قدیمی خودکار حذف نمی‌شوند.

## ارتقا از GitHub

```bash
sudo infrahub update
sudo infrahub update --version 0.2.0
```

حالت پیش‌فرض آخرین **release پایدار امضاشده** را از مخزن تنظیم‌شده می‌گیرد. ابتدا snapshot کامل می‌گیرد، سپس دانلود، بررسی امضا/سازگاری، اجرای مسیر ارتقا و بررسی سلامت انجام می‌شود. `helper.json` و `release-public.key` تنظیمات release هستند؛ token فقط‌خواندنی باید در فایل محافظت‌شده باشد. هنوز release واقعی منتشر نشده؛ نبود release یا کلید، خطای روشن می‌دهد و دستور main را کورکورانه deploy نمی‌کند. سازگاری انتشار امضاشده فعلی Ubuntu 24.04 است؛ برای Debian، manifest و مسیر انتشار سازگار باید در فاز انتشار آماده شوند.

برای دریافت تغییرات سورس قبل از انتشار release، شناسه **کامل ۴۰کاراکتری commit بازبینی‌شده** بدهید:

```bash
sudo infrahub update --commit FULL_40_CHARACTER_COMMIT
```

این حالت در Debian نیز مسیر سورس نصب‌شده را به‌روزرسانی می‌کند. ابتدا پشتیبان کامل می‌گیرد، سپس commit را با Git/HTTPS می‌گیرد و شناسه را تطبیق می‌دهد؛ شناسه commit جای امضای release را نمی‌گیرد. سورس جایگزین، تصویر جدید با tag مستقل ساخته، migration اجرا و سلامت بررسی می‌شود. `.env`، کلیدها، داده‌ها و تنظیمات site حفظ می‌شوند. مخزن فقط از تنظیمات root-owned خوانده می‌شود. فرمان‌ها قفل دارند؛ هیچ shell دلخواه یا Docker socket در برنامه وب اضافه نشده است. در خطا، پشتیبان و وضعیت maintenance حفظ می‌شود؛ rollback خودکار دیتابیس وعده داده نمی‌شود.

## بازگردانی

```bash
sudo infrahub restore /srv/infrahub-backups/infrahub-backup-TIMESTAMP.tar.gz --confirm
```

با checksum داخلی و خارجی اعتبار پشتیبان بررسی می‌شود. پیش از تغییر، یک snapshot از وضعیت فعلی نگه داشته می‌شود. سپس سورس و تصاویر قبلی، تنظیمات و دیتابیس بازگردانده می‌شوند. این عملیات داده‌های فعلی را بازنویسی می‌کند؛ `--confirm` لازم است. dump دارای DROP DATABASE برای بازسازی دقیق دیتابیس است؛ کاربر restore باید مجوز لازم داشته باشد و فرمان فقط روی دیتابیس برنامه استفاده شود. برای migration غیرقابل‌بازگشت، همین بازگردانی snapshot کامل مبناست؛ داده‌های پس از زمان پشتیبان از دست می‌روند.

برای نصب قدیمی، سورس ابزارهای جدید را طبق روش دستی دریافت کنید، بسته `python3-venv` لازم است و با `sudo python3 scripts/install_cli.py --root /opt/infrahub` فرمان ثبت می‌شود. در نصب آفلاین `--offline` فرمان backup/restore و commit را با Python استاندارد ثبت می‌کند؛ ارتقای امضاشده به محیط CLI آماده‌شده با wheelهای lock نیاز دارد. GitHub، apt، صدور گواهی و ارتقای واقعی سرور در این فاز اجرا نشده‌اند.
