# InfraHub آفلاین

دو فاز جدا داریم: **آماده‌سازی سرور با اینترنت، یک بار**؛ سپس **نصب و ارتقای برنامه کاملاً از بسته محلی**. ساخت هر بسته روی ماشین متصل به اینترنت انجام می‌شود، نه روی سرور آفلاین. کپی فایل با USB، دیسک یا شبکه داخلی انجام می‌شود. GitHub فقط مخزن توسعه سورس است؛ برنامه و updater به آن وصل نمی‌شوند. پروکسی وب و DNS انتخابی برای دسترسی کاربران شبکه محلی bridge دارند؛ بک‌اند و دیتابیس داخلی هستند. NAT خروجی bridge غیرفعال است، اما قطع فیزیکی/سیاست شبکه air-gapped همچنان مسئولیت شبکه سرور است.

## ساخت بسته روی ماشین متصل

نیاز: checkout سورس، Docker/Compose، Python و وابستگی‌های ابزار امضا/CLI در محیط ایزوله. از requirements.cli.lock با hash نصب کنید. کلید خصوصی Ed25519 باید روی ماشین امضاکننده و خارج از سورس بماند؛ کلید عمومی روی سرور از مسیر مستقل مورد اعتماد تأیید می‌شود. artifact شامل کلید خصوصی نیست. این اسکریپت انتشار GitHub یا upload image انجام نمی‌دهد.

```bash
# فقط یک بار روی ماشین امضاکننده، با مسیر محافظت‌شده بیرون سورس:
python scripts/create_signing_key.py --directory /PROTECTED/infrahub-signing
python scripts/build_offline.py --root . --output artifacts/infrahub-0.2.0 --signing-key /PROTECTED/infrahub-signing/private-signing.key
```

اسکریپت تصاویر backend/frontend را می‌سازد، MySQL/Caddy را می‌گیرد، DNS اختیاری را می‌سازد، تصاویر amd64 را ذخیره و wheelهای CLI برای Python 3.11/3.12/3.13 را با hash دریافت می‌کند. سپس سورس، images.tar و wheels داخل artifact امضاشده قرار می‌گیرند. خروجی پوشه شامل artifact، manifest، signature و پوشه prepare است. کل **پوشه خروجی** را منتقل کنید. حد استخراج ۳۲ GiB است؛ فضای کافی برای بسته، استخراج، تصاویر Docker و پشتیبان لازم است. build روی x86_64/amd64 انجام شود؛ ARM هدف تأییدشده ندارد.

## آماده‌سازی اولیه سرور با یک فرمان

پوشه بسته را کپی کنید. تا پایان این مرحله اینترنت لازم است:

```bash
sudo bash /srv/infrahub-package/prepare/scripts/prepare-server.sh --apply
```

اسکریپت آماده‌سازی را از سورس مورد اعتماد اجرا کنید؛ امضای manifest مربوط به artifact برنامه است، نه مجوز اعتماد خودکار به هر اسکریپت آماده‌سازی کپی‌شده. این فرمان OS/architecture را بررسی، پیش‌نیازها و Docker رسمی را نصب، سرویس Docker را برای reboot فعال و محیط Python ابزار مدیریت را با dependency lock آماده می‌کند. فرمان `infrahub-install` ثبت می‌شود. هیچ application/database شروع نمی‌شود؛ SSH، DNS میزبان و firewall تغییر نمی‌کنند. بسته‌های متعارض بدون حذف خودکار گزارش می‌شوند. اجرای بدون `--apply` تنها برنامه کار را نمایش می‌دهد. به جای چند دستور apt/pip/Docker، فقط همین یک فرمان است. برای آماده‌سازی از checkout سورس، مسیر `scripts/prepare-server.sh` است.

## نصب اولیه بدون اینترنت

پس از اتمام آماده‌سازی می‌توانید اینترنت سرور را قطع کنید. IP نمونه را جایگزین کنید:

```bash
sudo infrahub-install /srv/infrahub-package --public-key /srv/trusted-public.key --host 192.0.2.10 --tls local --apply
```

امضا و hash قبل از استخراج بررسی می‌شود. imageها با docker load و wheelها با pip --no-index نصب می‌شوند. تنظیمات/کلیدهای یکتا و مجوز پوشه‌ها ساخته، migration اجرا و رمز admin به شکل پنهان پرسیده می‌شود. `--admin` نام مدیر را تغییر می‌دهد. گواهی عمومی CA در config/local-root.crt برای اعتماد روی کلاینت‌هاست؛ کلید خصوصی توزیع نشود. گزینه `--tls none` فقط HTTP است؛ پورت‌ها با `--http` و `--https` قابل انتخاب‌اند. برای نام داخلی، DNS شبکه را تنظیم کنید یا `--dns local --address IP --bind LAN_IP` بدهید؛ DNS داخلی باید روی همان IP پورت 53 آزاد داشته باشد. Let’s Encrypt به اینترنت وابسته است و این installer آن را نمی‌پذیرد.

فرمان بدون `--apply` فقط بسته را اعتبارسنجی و برنامه نصب را نشان می‌دهد. تکرار روی نصب کامل، داده و کلیدها را حفظ می‌کند و نصب را جایگزین نمی‌کند؛ ارتقا فرمان جدا دارد. نصب نیمه‌کاره همان artifact با state pending قابل ادامه است. بسته‌ای با hash متفاوت ادامه نصب قبلی محسوب نمی‌شود.

## ارتقای آفلاین

نسخه جدید را روی ماشین آماده‌سازی بسازید، SemVer و migration guidance را به‌روز و کل پوشه بسته را روی سرور کپی کنید:

```bash
sudo infrahub update /srv/infrahub-package-new
```

ابتدا بسته امضاشده اعتبارسنجی می‌شود، snapshot کامل تاریخ‌دار گرفته و سپس تصاویر محلی، سورس و migration اعمال می‌شوند. هیچ docker pull/build، pip اینترنتی، GitHub یا git fetch اجرا نمی‌شود. کلیدها و فایل‌های خصوصی حفظ می‌شوند؛ تنظیمات ACME قدیمی به CA محلی منتقل می‌شود و مرورگرهای کلاینت باید CA محلی را اعتماد کنند؛ در شکست backup/maintenance باقی می‌ماند. `infrahub update` بدون مسیر فقط آخرین بسته‌ای را که **قبلاً محلی stage شده** انتخاب می‌کند، نه آخرین کد اینترنتی.

برای داشبورد:

```bash
sudo infrahub stage /srv/infrahub-package-new
```

metadata امن پس از بررسی امضا برای داشبورد آماده می‌شود. دکمه بررسی، metadata محلی را می‌خواند. نصب از داشبورد همچنان مجوز مستقل و helper root محدود می‌خواهد؛ فعال‌سازی سرویس helper باید در عملیات استقرار انجام شود. برنامه وب Docker socket ندارد.

## پشتیبان و بازگردانی

```bash
sudo infrahub backup
sudo infrahub restore /PATH/infrahub-backup-TIMESTAMP.tar.gz --confirm
```

پشتیبان فشرده شامل SQL، آپلودها، تنظیمات/کلیدها، سورس، wheelهای نسخه قبلی و تصاویر قبلی است. cache بسته‌های update در state/releases و کپی تکراری images.tar از سورس، در snapshot وارد نمی‌شوند؛ تصاویر واقعی Docker یک بار جدا ذخیره می‌شوند و تاریخ تهران دارد. حساس است؛ مجوز 600 جای رمزگذاری در ذخیره‌ساز را نمی‌گیرد. restore داده‌های فعلی را بازنویسی می‌کند و ابتدا snapshot فعلی می‌گیرد. برای migration برگشت‌ناپذیر، restore دیتابیس از backup لازم است و داده پس از backup از دست می‌رود. rollback خودکار تضمین نمی‌شود.

## وضعیت تأیید

منطق بسته، امضا، عدم درخواست شبکه، فرمان‌های بدون pull/build/index و مسیرهای خطا با fixture/mock و محیط ایزوله بررسی شده‌اند. یک بسته کامل با تصاویر و wheelهای واقعی و کلید امضای آزمایشی هم ساخته و محتوای آن بررسی شده است؛ این بسته آزمایشی برای اعتماد عملیاتی کاربر معرفی نمی‌شود. نصب واقعی روی Debian خام، انتقال به شبکه air-gapped و reboot میزبان باید در فاز استقرار تأیید شود. بسته عملیاتی یا کلید امضای واقعی کاربر در این تحویل تولید/منتشر نشده است.
